A neural network can't look at a bird card. It sees a row of numbers. This page follows one real decision from a recorded MCTS game, from the table to the numbers to the two networks that will learn from them. Every figure uses the real encoder and real data.

Two roads into one network

The network answers two questions: how good is this position (the value), and which move should I make (the policy). Click any box to jump to it.

Ground rules

Four rules every number follows

An encoder is a contract between the game and the network. These four rules shape every later decision on the page.

Every number has a name

Each block is built as a dictionary first, such as {"forest_2_eggs": 0.33, …}. The vector is its values in a fixed order. When the net does something strange, you can trace any input back to its meaning. Hover any cell on this page to see its name.

Everything lands in [0, 1]

A wingspan in centimetres (up to 277) next to an egg count (up to 6) would make wingspan dominate early training, just because of its units. So each value is divided by a known maximum, and values above the cap saturate at 1.0.

Only what you could see

Opponents' hands and bonus cards are zeros. Nothing depends on deck order. A test re-deals every hidden card and asserts the encoding doesn't move. If it leaked, the net would learn to cheat, and MCTS with re-dealt hidden cards would disagree with it.

Same layout for every player

"Me" and each opponent use the identical 847-number layout. One set of weights can read any player, and "me" always comes first. So the net learns "my position" rather than "seat 2's position".

Scaling, made visible: wingspan of all 170 birds

Top: dividing by 300 cm squeezes most birds into the left third, so the net would barely tell a sparrow from a jay. Bottom: log(wingspan) / log(300), which the encoder uses, spreads them out. The cost: no bird ever goes below about 0.4.

Block 0 · static, computed once

A bird becomes 45 numbers

Cards never change, so each of the 170 birds gets one fixed row: points, egg limit, wingspan, nest, habitats, food cost, power color and power template. That row is reused wherever the bird appears: on a board, in a hand, in the tray, or inside an action.

Nearest birds by these 45 numbers

Left: the card as our web app draws it. Right: the same card as the network reads it. Darker cells are closer to 1. Notice what the right side can't hold: the power's text. The net only sees its color and which of 21 templates it uses. An either/or cost ("1 invertebrate or 1 fruit") is stored as the average over the options, 0.5 each, plus the cost_is_or flag. The nearest-bird list shows the point of using features: birds that play alike end up close together, so what the net learns about one transfers to its neighbours.

Why features instead of a learned ID

The common alternative is an embedding table: bird #95 looks up a learned vector. It can learn anything, including power details we left out, but it learns each bird separately. With about 2,500 games and 170 birds, many birds appear in a few hundred positions at most. Features generalize from day one: a bowl-nest, 4-egg grassland bird looks like every other one.

What v1 leaves out

The net sees a power's color (when it fires) and its template (which of 21 effect kinds). It doesn't see the parameters: which food, which habitat, how many. Two birds with "gain 1 seed" and "gain 2 fish" look identical apart from their cost and habitat. A learned embedding added on top of the features is the cheap fix later.

Block 1 · one per player

A player is 847 numbers, and 87% of them are the board

The example is decision #116 of a real game from the mcts_joint_v2 tuning study: player 2 in round 3, about to place three eggs. They won 80–73. The board has 15 slots. Each slot holds 4 dynamic numbers (occupied, eggs, cached food, tucked cards) followed by the 45 static numbers of whichever bird sits there. Where a slot is (its habitat, its egg cost) is never stored as a value. The column position says it.

The whole player block, in vector order

Each row is one group, in the order the vector stores them. Hatched cells are hidden from this viewer and encoded as 0. Switch to "Your block, as the opponent sees it": your hand and bonus card disappear, but hand_size and bonus_card_count stay, because everyone at the table can count cards.

Row summaries are free hints

Each habitat row adds 4 numbers: what its action yields right now, whether it offers the "trade one for one more" bonus, the egg cost of its next empty spot, and how full it is. The net could derive all of these from occupancy. Deriving them takes capacity and data we don't have much of, and a test checks each one against what the engine does.

score_now

Bird points + eggs + cached food + tucked cards + banked round goals: everything anyone can count, scaled by 120. The value net would otherwise have to add up about 700 inputs to get the single most predictive number for who wins. It's computed from the board, because player.score is only refreshed at the end of a turn.

Turns are counted, not just scaled

A cube is one turn, so 5 cubes means exactly 5 more turns this round, and the encoder scales them by 8, the most a round ever starts with. Scaling alone keeps the information (the first layer can undo a division). It doesn't make "exactly the last turn" easy to find, and planning backwards from the end of the game is what strong play needs. So three columns state it directly: turns_left_game (this round's cubes plus every later round's allotment, over 26), and flags for exactly one turn left in the round and in the game. The cube is spent when the main action completes, so while choosing, "one turn left" means "this is my last turn".

A design choice worth understanding

Hands and trays are bags: summed, not listed

A hand can hold 0 to 12+ birds, but the vector needs a fixed width. The encoder adds the bird rows together and divides by 12, so hand_points means "total points in hand, as a fraction of a full hand of maximum birds". Order doesn't matter and the width is fixed. Something is lost, though.

Two different hands, one identical points column

Both hands hold 3 birds and 12 points, so hand_size and hand_points come out exactly equal. The left hand has one 9-point bird you may want to build toward; the right has three average ones. Other columns (cost, habitat) differ, but nothing says which points go with which cost. The same happens with properties: a grassland-bowl bird plus a wetland-cavity bird sums to exactly the same habitat and nest columns as a wetland-bowl bird plus a grassland-cavity bird. If a bonus rewards bowl birds in the wetland, only the second hand has one, and the bag can't say so.

The fix, a set encoder, gets its own section after Actions, because moves that name several birds have the same problem. Jump to Sets.

Block 2 · one per observation

The table, and the question being asked

The shared block holds 241 numbers. Public (124) is the table: tray, bird feeder, deck and discard sizes, the round, and the four round goals. Pending (113) is what the game is asking right now. Players (4) is the player count.

The pending block is the subtle one. Decisions #115 to #118 below come from the same player a few seconds apart, on almost the same board. #115 asks which action to take, #116 where the eggs go, #117 whether to run the power that laying eggs triggered, and #118 which bird that power should target. Without the pending block, the net would see four nearly identical inputs and have to produce four different kinds of answer.

Block 3 · one per legal move

Each legal move becomes 146 numbers

The obvious design is one output per possible move in the whole game. But the set of moves in Wingspan is huge and mostly empty: a huge space of egg distributions, of which at most 81 are legal at a time. So instead we describe each legal move with a vector and let the network score each one. The number of legal moves can vary freely, from 2 to 192 in our data.

An action vector has two parts. A one-hot kind (37 options) says what is being done, and the rest says to what: which birds (their averaged features, a choice the Sets section revisits), which bonus card, which board spots, which habitat, which foods, how many eggs or cards.

Why spots matter: lining actions up with the board

"Lay 2 eggs on bird #95" says nothing about where #95 sits. To judge it, the net needs that slot's current eggs, its row and the round goal ("eggs in forest"). With only bird features, it would have to match a 45-number pattern against 15 slots, and MLPs are poor at learned equality tests. With action_spot_forest_2 = 2/5, the action points at the same position the observation uses for forest_2_*. The net learns one rule per slot instead of one per bird-and-slot pair. A card in hand has no spot, so a tuck or discard leaves these 15 numbers at zero.

Keeping cards apart · experiment EXP-010 planned

Set encoders: transform each card, then add

The summed hand and the averaged birds of a move have the same flaw: adding cards together mixes up their properties. This section builds the fix one step at a time. First the failure, live. Then why no linear layer can repair it, why a single ReLU unit can, and how the fix plugs into the networks.

Step 1 · Two hands, one sum

Pick any two birds for each hand. The left half of each table is what the encoder adds up today: four of the 45 columns. The right half is four detector units, computed per card before adding. Each one is ReLU(habitat + nest − 1): it fires only when the habitat and the nest are on the same card. With the default hands, the raw sums come out identical, so the network can't know that only hand B holds a bowl bird for the wetland. The detector sums differ, so after adding, that fact is still there.

Step 2 · Why a linear layer can't fix it

One unit, wetland + bowl − 1, on the hands above, with and without the ReLU. Without it, the card values just add up: Σ(w·xᵢ + b) = w·Σxᵢ + n·b. That depends only on the raw sums and the card count, so two hands with equal sums get equal outputs, whatever the weights. The ReLU clips the negative card to 0 before the sum, and that clip is what keeps the cards apart.

Step 3 · One ReLU unit is an AND gate

With weights +1, +1 and bias −1, the unit only exceeds 0 when both inputs are 1. That's why a hidden layer of such units can detect any "property X and property Y on this card". In the real network nobody writes these weights: φ has 64 outputs, and training finds whichever combinations help predict MCTS's choices and the game result.

Step 4a · One card: 45 numbers in, 64 out

Every bird has a fixed row of 45 numbers in the bird table: points, egg limit, wingspan, nest, habitats, cost, power colour and template. The hand is stored as bird ids, and looking an id up gives that bird's row [45]. φ (phi) is a small network, 45 → 64 → 64, with about 7,000 weights. It turns the row into 64 new numbers. Think of them as 64 questions it asks about the card. Nobody chooses the questions; training does. Here the four detectors from Step 1 stand in for 4 of them, and the dashed cells are the other 60.

Step 4b · A whole hand: the same φ on every card, then Σ

Hand B from Step 1, one row per card. Every card goes through the same φ, with the same weights. Σ then adds the outputs column by column, so the first column of the result means "how many cards in this hand answered question 1". A hand of 1 card or 17 still comes out as 64 numbers.

The last row is padding. Training works on a batch of decisions at once, stored as one rectangular block of numbers, so shorter hands get dummy rows up to the longest hand in the batch, plus a mask: 1 for a real card, 0 for padding. φ of a dummy row isn't zero, because each layer adds a constant, so φ's output is multiplied by the mask before the sum. When the bot plays one decision at a time, there's no padding at all.

Step 4c · Joining the rest: concat, then the MLPs

Concat puts two lists end to end. The 1,935 observation numbers are followed by the hand's 64, giving one list of 1,999 (the bars above, to scale). Nothing is added here: the adding happened across cards, in 4b. The next network needs one input list, so its first layer simply gets 64 more inputs, each with its own weights.

An MLP (multi-layer perceptron) is a stack of simple steps: multiply the list by a table of weights, add constants, set negatives to zero (ReLU), and repeat. The trunk MLP reads the whole position once per decision and compresses it into h, 256 numbers. It's called the trunk because the value head and the policy head branch off it, like branches off a tree. The action MLP turns each legal move, together with the 64 numbers from its own set encoder φₐ, into aₖ: 256 numbers in the same space as h. It runs once per legal move, with the same weights each time. The policy then scores each move as h · aₖ.

All of it trains together. On every batch, the error flows back from the loss through the heads, the trunk, the concat and the sum into φ, and every weight moves a little. φ isn't trained separately, and nobody tells it what to detect.

Step 5 · Sum, mean or max?

The "wetland ∧ bowl" detector over three hands, pooled three ways. Sum counts the matching cards. Mean divides by hand size, so one match in a hand of one looks like two in a hand of two. Max only says "at least one". The hand uses sum. An egg distribution lists a bird once per egg, so sum also counts eggs.

Three properties for free

Order doesn't matter. Addition doesn't care which card comes first, so shuffling a hand changes nothing.

Any number of cards. A 17-card hand is 17 rows. Nothing is divided by a cap, so nothing saturates. The cap question for hand_size doesn't apply here.

Nothing is lost in principle. Zaheer et al. (2017) proved that any calculation on a set, meaning one whose answer can't depend on the order of the items, can be done in three steps: apply the same function φ to each item, add up the results, then apply a second function ρ (rho) to the total. Think of an election: φ turns each ballot into tally marks, the tallies are added, and ρ reads the totals to decide. Here the trunk MLP plays ρ. The proof assumes φ has enough outputs to count everything that matters; 64 is a practical bet, not a guarantee.

Where it applies, and where it doesn't

Applies: the hand and the tray in the observation, and every move that names several birds. Keeping 2 of 5 birds at setup is one of 64 options, and today all 64 are told apart only by the average of the kept birds. Taking 2 birds from the tray and spreading eggs over several birds work the same way.

Doesn't apply: bonus cards and the board. Each bonus card has its own identity column, so adding cards just lists which ones you hold, and a card's identity fixes all its parameters. Each board slot has its own 49 columns, so nothing on the board is added together.

What it still can't see

φ looks at one card at a time. Two birds that only matter together, like two birds that need the same scarce food, are combined after the sum, by the trunk, from the pooled detectors. So is the link between a card and the board: "does this bird fit my open wetland slot". Attention (a set transformer) lets each card look at the other cards and at the board slots before pooling. It's the next step if EXP-010 shows that sets matter.

Step 3 · the replay dataset planned

One training example, and a surprise in the labels

decisions.parquet stores, for every decision with more than one legal move, the move strings, the MCTS visit counts and the mean value of each child. It doesn't store the state, so the dataset builder replays the game from game_seed, auto-applies forced single-legal steps, and encodes the state at each recorded decision. I replayed 10 games this way and every legal-move set matched exactly.

The visit counts are almost exactly uniform

Across a 60,000-decision sample, the median normalized entropy of the visit distribution is 0.999, where 1.0 means perfectly uniform. That holds in every phase. The reason is in the UCT formula MCTS uses to pick which child to explore: Q + c·√(ln N / n). The values of sibling moves differ by about 0.012 (median), while the exploration bonus is about 0.5. Exploration wins every comparison, so MCTS spreads its 1,500 simulations evenly and the final pick comes down to tiny differences in Q.

This has two consequences. For training, raw visit counts as the policy target would teach the net to play uniformly at random. For the engine, it probably explains why tuning the exploration constant came out flat: every value in the 0.3–8 range was too large compared with the Q differences.

Choosing the policy target

Value targets

Every decision in a game shares that game's result: z = +1 for the winner and −1 for the loser. The final score difference (here +7, scaled by 50) is a second, richer target: a 1-point loss and a 30-point loss are both z = −1 but very different positions. The root value MCTS stored isn't used, because the study's arms used three different value functions, so it comes on three different scales.

What one example looks like on disk

Step 4 · the networks planned

Two heads, built apart, then merged

The plan is to train a value net first, then a policy net, and only then merge them into one network with a shared trunk and two heads, as AlphaZero does. Building them apart means each failure has one cause. If the merged net plays badly, you won't know which half is wrong. Pick a stage below.

The policy head is a tiny attention step

The observation trunk produces h, a 256-number summary of the situation. The action MLP turns each legal move into aₖ in the same 256-dimensional space. The score of move k is the dot product h · aₖ. This is the query–key product from transformer attention: h asks "what kind of move is good here?", each aₖ answers "this is what I am", and the dot product measures how well they match. A softmax over the K scores gives the policy.

Why the value net needs more care

The policy net gets one label per decision: 438,686 of them. The value net gets one label per game, shared by about 170 decisions that all look alike. So it effectively sees 2,550 outcomes, which is easy to memorize. Hence the score-difference target, a small network, weight decay, and a game-level split. In the merged net, the value loss is usually down-weighted so it can't drag the shared trunk into overfitting.

Batching moves of different counts: pad, then mask

A batch of the four example decisions has 3, 14, 2 and 4 legal moves. They're padded to 14 so the batch is one tensor, [4, 14, 146]. Before the softmax, padded slots get a score of −∞, so they receive exactly 0 probability and 0 gradient. In the data, 98.5% of decisions have 20 moves or fewer; the rare 64-to-192-move decisions can go in their own batches.

Step 5 · plugging the nets into search planned

Where the two heads go inside MCTS

The nets don't replace search; they make each simulation smarter and cheaper. The policy tells MCTS which children deserve visits before it has tried them. The value replaces the random rollout to the end of the game with one forward pass.

One simulation today built
  1. Select a path down the tree using UCT: Q + c·√(ln N / n). Every child starts equal.
  2. Expand a new child (progressive widening limits how many).
  3. Roll out with random moves to the end of the game: about 150 more decisions, all random.
  4. Back up the final result into every node on the path, one value per player.
One simulation with the nets planned
  1. Select using PUCT, where the policy's prior P(s,a) decides which children look promising before any visit.
  2. Expand a child and evaluate the net once: P for its moves, v for the position.
  3. No rollout. The value head's v stands in for "play randomly to the end and see".
  4. Back up v exactly as before.

Hover a term to see what it does.

The uniform visits matter here too

PUCT has the same scale problem as UCT. If Q differences are about 0.01 and the bonus is about 0.5, the policy prior will dominate and the value head will barely steer. AlphaZero-style implementations normalize Q to [0, 1] using the minimum and maximum values seen in the tree (MuZero does this). Then c means the same thing in every position. It's a small change, and probably worth testing on the current UCT before any network exists.

The loop this all builds toward (step 6)

Each lap, a stronger search produces better labels, which trains a stronger net, which makes a stronger search. The first lap starts from plain MCTS games because training from random self-play would cost more compute than a laptop and a homelab can spare (hypotheses H6/H7).
